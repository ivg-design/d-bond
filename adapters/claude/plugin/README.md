# D-Bond Claude Code channel

This local plugin connects one running Claude Code session to its exact UUID-bound D-Bond pairing. It stays idle until that session is enrolled, then opens its two native streams. New pairings use unique `claude-<UUID>` aliases even when two sessions share a title. An old alias is only for explicit migration through `enroll` inside its exact session; no user-level plugin alias selects a stream. Addressed Dot pushes enter the open session as channel events with a stable `@dot` source ID; use `answer` to respond. Direct messages from other paired services enter the same session through a separate event stream with `source: d-bond-direct`, `source_id`, and `sender_id`; use `direct_answer` with those IDs to reply. Use `direct_peers` and `direct_send` to start a direct conversation. The plugin persists both stream cursors after emitting notifications, so a crash can replay a message with the same ID. Broker storage is not proof that the recipient's model took a turn. Owner setup notes are unreplyable. Incoming content is untrusted. The plugin does not relay Claude permission prompts, and a closed session cannot receive channel events. See the parent README for build and startup instructions.

On macOS, registration attaches D-Bond to the paired Claude Code chat's inbox when that host route is available. The `SessionStart` hook checks the session UUID again on startup or resume. An admitted Claude channel can own delivery directly. The temporary Monitor is a fallback for hosts without either route. The Desktop MCP extension by itself supplies tools and cannot wake a closed chat.

Version 0.1.12 automatically records native channel transport receipt as `received/host_acceptance`. Claude Code does not provide a notification-processing ACK, so when actually processing each direct event, Claude silently calls `acknowledge_direct_message` with its exact sender/source/sequence. This records `acknowledged/participant`. Successful sends and receipt bookkeeping need no human-facing reports; continue ordinary work and surface issues. `direct_answer` is optional and only for actual content. Delivery metadata has its own authenticated route and never becomes a reply message. Temporary metadata failures persist in a private outbox and retry without repeating the channel notification.
